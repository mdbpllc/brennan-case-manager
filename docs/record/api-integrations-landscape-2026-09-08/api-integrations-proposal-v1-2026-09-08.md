## §1 — THE DECISION ABOVE EVERY OTHER: the server-side identity, and a proposed shape for it

Almost every integration worth having on this list is a **background watcher** — envelope acceptances arrive when the clerk sends them, e-signature reminders stall for weeks, records custodians go quiet, QuickBooks refresh tokens rotate whether anyone is signed in or not. The app today has no place for any of that to run: the browser SPA exists only while a tab is open, and the registration deliberately holds no secret. `Q-WF-4` asks the right question and it has been open since 2026-08-15 with three consumers stacked behind it. **This memo proposes an answer, put as a starting point.**

### 1.1 The proposal — "the integration runner"

**One runner, three parts, all inside the platform the app already pays for:**

| Part | What it is | Why this and not something else |
|---|---|---|
| **Execution** | **Supabase Edge Functions, scheduled from Postgres** — Supabase's documented pattern: *"The hosted Supabase Platform supports the `pg_cron` extension, a recurring job scheduler in Postgres"* combined with the *"`pg_net` extension … [which] allows us to invoke Edge Functions periodically"*, with the call's auth token kept in Vault — *"we recommend storing them in Supabase Vault"* (Supabase Docs, *Scheduling Edge Functions* **[FETCHED 2026-09-08]**; the Cron module page at `supabase.com/modules/cron` **[SEARCH ONLY]**). Edge Functions are public HTTPS endpoints, so Graph change notifications (webhooks) have somewhere to land and something to answer the 10-second validation handshake the WF spec §4.2 records. | The two functions that already exist are Edge Functions; the design of 2026-07-25 chose them for the LegiScan poller (D4) *because* the work is text I/O with no PHI. The P1 laptop sleeps and travels (the `#137` capture's own words) and is the wrong host for anything that must run unattended — it stays the host for PHI-touching AI, which is a different job. |
| **Identity** | **A SECOND Entra app registration, a confidential client with a certificate (not a secret string), holding APPLICATION permissions for Exchange data only** — `Mail.Read` first, `Mail.Send` later, calendar and contacts if those rows are built — **scoped with Exchange Online RBAC for Applications to Michael's mailbox only.** (`CallRecords.Read.All`, §3.1, is a Teams permission outside Exchange and outside this scoping mechanism — tenant-wide by nature; it is not part of this registration's first consent and is proposed only at the hire, if that exposure is accepted.) Microsoft's page: RBAC for Applications *"allows admins to grant permissions to an application that's independently accessing data in Exchange Online. This grant can be paired with a scope of access (resource scope) to specify which mailboxes an app can access"*, and it *"replaces Application Access Policies"* (Microsoft Learn, "Role Based Access Control for Applications in Exchange Online", page updated 2026-08-21 **[FETCHED 2026-09-08]**). **What that page does NOT do: scope anything outside Exchange.** A file permission such as `Files.Read.All` is OneDrive/SharePoint data, and RBAC for Applications says nothing about it — so **no app-only file permission is proposed anywhere in this memo**; every file row in §3 runs delegated, in the browser, as Michael. (If a background file read is ever wanted, SharePoint has its own per-site consent model, `Sites.Selected`; **not researched this sitting, not established, not proposed.**) The existing SPA registration stays exactly as it is — interactive, delegated, secretless. | The WF spec's structural finding is that app-only permission is *"tenant-wide by default unless Exchange Application RBAC scopes it to the single mailbox"* (§4.3 item 3). Scoping to one mailbox is what turns "an app that can read every mailbox in the tenant" into "an app that can read Michael's" — and at the paralegal hire, the scope is widened by one mailbox, not re-architected. A certificate rather than a client secret because the credential then never exists as a pasteable string. |
| **Custody** | **Two tiers.** Static keys (LegiScan, a CourtListener token, an SRFax or Twilio key) stay where gate 4 already puts them: Edge Function secrets. **Rotating values** — the QuickBooks refresh token, Graph change-notification subscription ids and `deltaLink`s, e-signature webhook secrets — go in a new `integration_credentials` table whose secret columns are held in **Supabase Vault** (encrypted at rest, readable only by the function's role), with RLS denying `authenticated` entirely. The runner writes back the rotated value in the same transaction that consumed the old one. | The QBO memo's exact finding (§4.2): *"the discipline transfers; the mechanism does not"* — a hand-rotated static key has no home for a value the integration itself must overwrite every 24 hours. Gate 4's model needs a second shelf, not a replacement. |

**What it costs, and whose hand:** one new app registration and its admin consent — **Michael's hand** (the same act as 2026-07-26); the RBAC role assignment — a PowerShell act in Exchange Online, **his sign-in**, with a Code session drafting the exact commands; the Supabase Cron schedule and the Vault setup — a Code session; and **the proving step**, which costs nothing new: **deploy the two PHI-free Edge Functions already written** (`statute-fetch`, `legiscan-poller`; the `disclosures-writer` stub is not touched by this step — its deployment is `H12-v`'s act). The QBO memo says a QuickBooks integration *"would be the thing that proves"* the substrate; better to prove it on a PHI-free, static-key function whose failure mode is a missing statute chapter than on the firm's books.

### 1.2 The PHI consequence, which is the real cost

The moment the runner reads a mailbox, **mail bodies and attachments with PHI can land in Supabase.** The record has treated Supabase as "the database" and has not asked whether the platform is under a BAA. Supabase's own pages: *"Organizations must have a signed BAA with Supabase and have the … HIPAA add-on enabled when dealing with PHI"*; a project is then set to *High Compliance* mode, which mandates *"Enabling Point in Time Recovery which requires at least a small compute add-on,"* SSL enforcement, network restrictions, and connection logging (Supabase Docs, "HIPAA Projects" and "HIPAA Compliance and Supabase" **[FETCHED 2026-09-08]**; **plan eligibility is not stated on those pages** — Supabase's own form decides, and a GitHub discussion titled *"HIPAA Compliance add-on with Pro-Plan?"* exists **[SEARCH ONLY]**, which is a hint and not a fact).

**Two ways to hold this, both put:**

- **(a) Metadata-first ingest.** The runner stores *envelope* facts only — sender, recipients, subject, dates, thread id, attachment names and hashes, the classification, the matter suggestion — and a pointer back to the message in Exchange. Bodies and attachments are read in the browser, on demand, through the delegated scope, and never persisted. PHI stays in Microsoft's tenant — where it already is today, in the mailbox. Microsoft's HIPAA page, as the `h12-v` memo read it, says its BAA is *"available … by default to all customers who are covered entities"* through the Online Services DPA (**[RECORD]**, §3.5) — **that establishes availability, not execution: whether the firm's own tenant has that BAA in force is not on the record and is a fact for Michael** (a named look, §6). Cost: subject lines and attachment names can themselves carry PHI (a client's name plus "MRI results.pdf"), so even this is not PHI-free — it is PHI-thin, in the sense the disclosures work rejected for the model call: the stripped-chronology approach was REJECTED at `#130` (*"dates of service are themselves identifiers, and a chronology tied to a matter with one plaintiff is re-identifiable"*, as `hipaa-deidentification-entry-drafts-2026-09-01.md` records it), and the REQ-CAPTURE's own words are *"No scrubbing, no thinning. The BAA is the mechanism that makes it lawful; content engineering is not."* **[RECORD]** Whether PHI-thin is acceptable for a *mail index that never leaves the firm's own two vendors* is a different question from whether it is acceptable for a *model call to a third*, and it is Michael's — this memo does not answer it.
- **(b) Full ingest under a Supabase BAA.** Sign the BAA, enable the add-on, flip the project to High Compliance, and let the runner store what it reads. Cost: the add-on and a compute add-on for PITR (figures not read; **not estimated**), and the security-advisor obligations the pages describe. Benefit: WF-4 (LOP medical), WF-7 (records) and the chronology drop already need PHI in the database, so this is a cost the project will pay anyway the day a real chronology is dropped — the question is only *when*.

**Proposed default, named so it can be overruled: (a) until go-live and the first real PI chronology, then (b) as a go-live-adjacent act.** And a flag that stands regardless of the choice: **the chronology drop zone (`AS-Q4`, built, fixture-only) stores extracted chronology TEXT in Supabase** — BUILD-STATE: *"the FILE IS NEVER STORED, only its text (`AS-Q4`)"* and *"THE AMENDMENT'S FIVE CARRY PHI — a chronology's extracted text above all"* — **so the first real drop puts PHI in the database before any mail integration exists** (today: *"NO REAL CLIENT DATA HAS EVER ENTERED THE APP"*). The Supabase BAA question is therefore not an integration question at all; it is a pre-condition of the first real chronology drop, and it is not on the go-live floor because the floor is *"GO-LIVE = real case/party/client/SOL data hand-entered into the core app, NOTHING MORE."* **`Q-API-1`, §6.**

## §2 — HOW INTEGRATIONS FIT THIS APP: five rules, all proposed

**Rule 1 — three execution places, chosen by the data class, never by convenience.**

| Place | Runs when | Credential | Carries | Examples |
|---|---|---|---|---|
| **Browser SPA** (exists) | a tab is open; user-initiated | delegated, per-browser, no secret | anything Michael can already see | calendar push; on-demand mail read; on-demand QBO read (the memo notes QBO's read path *can* be user-initiated); Graph PDF conversion; OneDrive window |
| **Integration runner** (proposed, §1) | on schedule or on webhook | app-only certificate; Edge Function secrets; Vault | PHI only under the Supabase BAA (§1.2) | mail intake; LegiScan; statute refresh; e-signature and SMS webhooks; QBO token rotation; backup verification |
| **P1 local service** (designed, T3) | when the laptop is awake | none leave the machine | PHI-touching AI | transcription; bill/EOB ingestion (Phase 1b); a local model if `H12-v` goes that way |

**Rule 2 — inbound events are STAGED, never auto-filed.** The transcript inbox already embodies this (auto-file OFF, D1). Every inbound integration lands in one staging surface — the existing `/inbox` generalized from "transcript staging" to "everything that arrived" — with a source, a confidence, a suggested matter, and a confirm control. The `email-workflow-requirements.md` constraints apply on their face: hard ignore layer first, dedupe on the pipeline's key, human routing for client mail. Nothing writes a calendar event, a deadline, or a party record without a click, with one recorded exception the heartbeat design already names: an e-filing acceptance from a known sender may auto-arm the next thread (`case-heartbeat-design.md` §6 #5) — and even that arms a nudge, not a record.

**Rule 3 — outbound writes are idempotent and reconciled.** The Outlook duplicate defect is the exhibit: a push with no durable external id strands a copy forever. Every outbound integration gets an `external_refs` row (`system`, `external_id`, `local_table`, `local_id`, `last_synced_at`, `sync_status`) *before* the remote call, keyed so a retry finds its own prior attempt; the calendar push migrates onto it (fixing the defect's class, whatever its cause). The record notes the substrate is absent today (§0 item 13) — this is the one schema act every integration shares, and it is a migration only when Michael authorizes one.

**Rule 4 — PHI class is decided per integration before auth is designed.**

| Class | Meaning | Members |
|---|---|---|
| **0 — never PHI** | the traffic is public law or the firm's own credentials; a client is never named | LegiScan, statute fetch, eCFR, CourtListener (authority cites only — the design says *"never client names, facts, or case details"*), PACER, NPPES, Postmark auth mail, Bookings availability |
| **1 — confidential, not PHI** | client identity and money or filing facts, privileged but not health data | QuickBooks, LawPay-class payments, e-filing envelope notices, process serving, e-signature of engagement/fee documents, court dockets |
| **2 — PHI** | health information or documents that carry it | mail intake on a PI file, OneDrive documents, chronology text, medical-records fax, client SMS, the model call, the backup copy, e-signature of HIPAA authorizations |

Class 2 needs a signed BAA with **every** vendor in the path — including the platform holding the data — and Postmark, which *"cannot sign any Business Associate Agreements"* (Postmark Support, "Is Postmark HIPAA compliant?" **[FETCHED 2026-09-08]**), is therefore never a channel for anything but sign-in links. **App notifications that could name a client or a provider go out through Graph `Mail.Send` from Michael's own mailbox, not through Postmark** — which is a design consequence worth writing down now, before a "send me a reminder" feature reaches for the SMTP that is already wired.

**Rule 5 — Microsoft is the tenant; everything else is a vendor.** Graph is the default for calendar, mail, files, contacts, chat, call metadata, scheduling and PDF conversion. A non-Microsoft vendor enters only where Microsoft has no surface (payments, SMS with attachments, fax, e-signature webhooks, legislative data, case law, backup independence) — and each such vendor is a credential to custody, a BAA to sign or a data-terms review, and a row in `external_refs`.

## §5 — WHERE CLAUDE DISAGREES WITH SOMETHING ON THE RECORD, SAID PLAINLY

Three places, each put as a question rather than a correction, because each stands on a ruling or a ruled direction:

1. **The WF spec treats the server-side identity as a single question with one answer.** It may be two: an *interactive* identity (delegated, browser) and a *background* identity (app-only, runner) can coexist on two registrations, and most of the value in §3 comes from the delegated half — PDF conversion, on-demand mail bodies, the OneDrive window, `Mail.Send`, QBO reads — which needs no runner at all. Ruling `Q-WF-4` as "two registrations, two jobs" unblocks the browser half immediately while the runner is built. *Put as `Q-API-2`'s option text, not asserted.*
2. **The record's BAA attention has been on the model vendor and the backup vendor, and not on the database.** That is not an error — nobody asked — but the chronology drop zone already stores PHI text, so the first real PI chronology needs the Supabase question answered whether or not any integration is ever built. *`Q-API-1`.*
3. **"Read-only first" for QuickBooks is a property of our code, not of the grant** — the memo already says this. What this memo adds is that the same is true of every app-only **Exchange** permission (mail, calendar, contacts) until Exchange RBAC for Applications scopes it to a mailbox — and that the scoping act belongs in the same sentence as the consent act, never after it. Outside Exchange the page gives no scoping mechanism at all, which is why no app-only file permission is proposed (§1.1).
