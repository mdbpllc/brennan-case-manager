## §1 — THE DECISION ABOVE EVERY OTHER: the server-side identity, and a proposed shape for it

Almost every integration worth having on this list is a **background watcher** — envelope acceptances arrive when the clerk sends them, e-signature reminders stall for weeks, records custodians go quiet, QuickBooks refresh tokens rotate whether anyone is signed in or not. The app today has no place for any of that to run: the browser SPA exists only while a tab is open, and the registration deliberately holds no secret. `Q-WF-4` asks the right question and it has been open since 2026-08-15 with three consumers stacked behind it. **This memo proposes an answer, put as a starting point.**

### 1.1 The proposal — "the integration runner"

**One runner, three parts, all inside the platform the app already pays for:**

| Part | What it is | Why this and not something else |
|---|---|---|
| **Execution** | **Supabase Edge Functions, scheduled from Postgres** — Supabase's documented pattern: *"The hosted Supabase Platform supports the `pg_cron` extension, a recurring job scheduler in Postgres"* combined with the *"`pg_net` extension … [which] allows us to invoke Edge Functions periodically"*, with the call's auth token kept in Vault — *"we recommend storing them in Supabase Vault"* (Supabase Docs, *Scheduling Edge Functions* **[FETCHED 2026-09-08]**; the Cron module page at `supabase.com/modules/cron` **[SEARCH ONLY]**). **[v2] As a Graph webhook endpoint the function does ONE thing: answer the 10-second validation handshake, and for every notification *"validate and persist the notification in a queue on your endpoint and return `202 Accepted` status code within the 3-second window"* — Microsoft's own instruction (Microsoft Learn, *webhook delivery* **[FETCHED 2026-09-08]**) — into Supabase Queues (`pgmq`, *"a Postgres-native durable Message Queue system with guaranteed delivery"* **[FETCHED 2026-09-08]**), where a scheduled worker drains it. The limits that bound this are stated, not assumed: 256 MB; *"Maximum CPU Time: 2s (Amount of actual time spent on the CPU per request - does not include async I/O.)"*; 400 s wall clock on paid plans; 150 s idle timeout (`supabase.com/docs/guides/functions/limits` **[FETCHED 2026-09-08]**) — an acknowledge-and-enqueue does negligible CPU work against a 2-second budget (**a reasoned claim, not a measurement**; a build session measures it before relying on it); cold-start latency is not quantified on that page and is **not established**. Two further jobs the runner owns, as cron entries: **subscription renewal** (Outlook message/event subscriptions expire at 10,080 minutes, under seven days — 1,440 with resource data; **[FETCHED 2026-09-08]**) and a **periodic delta-query sweep** as the backstop for anything a webhook missed — Microsoft's documented pattern: *"use delta query to request all changes since the last time it made the request"* (**[FETCHED 2026-09-08]**); a missed 3-second window is itself *"retried at exponential backoff intervals"* for up to four hours with the timeout extended to ten seconds, so a cold start delays a notification and does not lose it. **And Microsoft names the alternative on the same page:** *"If your endpoint is unable to meet these performance characteristics, consider using Event Hubs or Event Grid as a target for receiving notifications"* — Event Hubs delivery needs no validation reply, and its credential is **either** a connection string held in Azure Key Vault **or** an Entra RBAC role assignment on the event hub (the page says SAS authentication will be deprecated and recommends Entra RBAC) (**[FETCHED 2026-09-08]**). That is the Azure runner, §1.3.** | The two functions that already exist are Edge Functions; the design of 2026-07-25 chose them for the LegiScan poller (D4) *because* the work is text I/O with no PHI. The P1 laptop sleeps and travels (the `#137` capture's own words) and is the wrong host for anything that must run unattended — it stays the host for PHI-touching AI, which is a different job. **[v2]** The webhook endpoint's job is deliberately tiny so that the platform's limits are irrelevant to it; the work happens in the drained queue, on the runner's own clock. |
| **Identity** | **A SECOND Entra app registration, a confidential client with a certificate (not a secret string), holding APPLICATION permissions for Exchange data only** — `Mail.Read` first, `Mail.Send` later, calendar and contacts if those rows are built — **scoped with Exchange Online RBAC for Applications to Michael's mailbox only.** (`CallRecords.Read.All`, §3.1, is a Teams permission outside Exchange and outside this scoping mechanism — tenant-wide by nature; it is not part of this registration's first consent and is proposed only at the hire, if that exposure is accepted.) Microsoft's page: RBAC for Applications *"allows admins to grant permissions to an application that's independently accessing data in Exchange Online. This grant can be paired with a scope of access (resource scope) to specify which mailboxes an app can access"*, and it *"replaces Application Access Policies"* (Microsoft Learn, "Role Based Access Control for Applications in Exchange Online", page updated 2026-08-21 **[FETCHED 2026-09-08]**). **What that page does NOT do: scope anything outside Exchange.** A file permission such as `Files.Read.All` is OneDrive/SharePoint data, and RBAC for Applications says nothing about it — so **no app-only file permission is proposed anywhere in this memo**; every file row in §3 runs delegated, in the browser, as Michael. (If a background file read is ever wanted, SharePoint has its own per-site consent model, `Sites.Selected`; **not researched this sitting, not established, not proposed.**) The existing SPA registration stays exactly as it is — interactive, delegated, secretless. | The WF spec's structural finding is that app-only permission is *"tenant-wide by default unless Exchange Application RBAC scopes it to the single mailbox"* (§4.3 item 3). Scoping to one mailbox is what turns "an app that can read every mailbox in the tenant" into "an app that can read Michael's" — and at the paralegal hire, the scope is widened by one mailbox, not re-architected. A certificate rather than a client secret because the credential then never exists as a pasteable string. **[v2]** A certificate also *expires*, and a solo firm has no IT staff to remember it: its expiry is a **firm obligation** in exactly the FO module's sense (a date, a name, lit until done, with a lead), and the acceptance test for the RBAC assignment is the challenger's, adopted in substance — **before go-live, prove that a second mailbox returns 403**; consent no tenant-wide `Mail.Read` without the scope assigned in the same act. ### 1.2 The PHI consequence, which is the real cost

The moment the runner reads a mailbox, **mail bodies and attachments with PHI can land in Supabase.** The record has treated Supabase as "the database" and has not asked whether the platform is under a BAA. Supabase's own pages: *"Organizations must have a signed BAA with Supabase and have the … HIPAA add-on enabled when dealing with PHI"*; a project is then set to *High Compliance* mode, which mandates *"Enabling Point in Time Recovery which requires at least a small compute add-on,"* SSL enforcement, network restrictions, and connection logging (Supabase Docs, "HIPAA Projects" and "HIPAA Compliance and Supabase" **[FETCHED 2026-09-08]**). **[v2] The plan eligibility v1 could not find on those pages is on the pricing page, and it is the memo's most consequential correction:** HIPAA is *"Not included in"* Free and Pro and *"Available as paid add-on"* on **Team — *"From $599 / month"*** — and Enterprise; PITR is *"$100 per month per 7 days retention"*; the Small compute High Compliance requires is **$15** (`supabase.com/pricing` **[FETCHED 2026-09-08]**). **Path (b) below therefore starts at roughly $714/month before the add-on's own unpublished price, against Pro's *"From $25 / month"*.**

**Two ways to hold this, both put:**

- **(a) Pointer-only ingest** **[v2 — was "metadata-first"; the challenge's A-7/W-4 accepted].** The runner stores a **pointer and a classification, nothing else**: the Graph message id, received-at, the pipeline's dedupe key where it is not PHI (an e-filing envelope number is not; a claim number may be), a classification **enum** the function computes and discards its inputs for, and a suggested matter. **No subject line, no sender display name, no attachment filename is stored** — each can be PHI on a PI file (a client's name beside "MRI results.pdf"). The challenger's point, accepted as a design rule and not as a legal finding: HIPAA's definition of protected health information carries no "thin" class (the challenger's cite, 45 C.F.R. § 160.103 — **UNVERIFIED**, a registry candidate under `Q-WF-6`; not characterized further here). The staging inbox shows subject and sender by reading them *live* in the browser through the delegated scope, never from the database. Bodies and attachments likewise. PHI stays in Microsoft's tenant — where it already is today, in the mailbox. Microsoft's HIPAA page, as the `h12-v` memo read it, says its BAA is *"available … by default to all customers who are covered entities or business associates under HIPAA"* through the Online Services DPA (**[RECORD]**, §3.5) — **that establishes availability, not execution: whether the firm's own tenant has that BAA in force is not on the record and is a fact for Michael** (a named look, §6). Cost: less useful offline — the inbox is only as good as the live read — and a discipline to keep, because the project's own words on thinning govern here too: the stripped-chronology approach was REJECTED at `#130` (*"dates of service are themselves identifiers, and a chronology tied to a matter with one plaintiff is re-identifiable"*, as `hipaa-deidentification-entry-drafts-2026-09-01.md` records it), and the REQ-CAPTURE says *"No scrubbing, no thinning. The BAA is the mechanism that makes it lawful; content engineering is not."* **[RECORD]** Pointer-only is not thinning: it stores no content at all. **[v2]** Whether even the pointer row (a message id beside a matter id) is acceptable without a Supabase BAA is put in `Q-API-4`, not answered.
- **(b) Full ingest under a Supabase BAA.** Sign the BAA, enable the add-on, flip the project to High Compliance, and let the runner store what it reads. Cost **[v2]**: the Team plan (from $599/month), PITR ($100/month per 7 days), Small compute ($15/month), the add-on's own unpublished price, and the security-advisor obligations the pages describe — **≥ $714/month before the add-on** **[FETCHED 2026-09-08]**. Benefit: WF-4 (LOP medical), WF-7 (records) and the chronology drop already need PHI in the database, so this is a cost the project will pay anyway the day a real chronology is dropped — the question is only *when*.

- **(c) The pointer architecture across the board** **[v2 — the challenge's ALT-4; TOUCHES A RULING].** PHI text never enters Supabase: chronology extracts stay on the P1 or in OneDrive, mail bodies stay in Exchange, documents stay in OneDrive, and Supabase holds matter ids, `driveItemId`s, `messageId`s, amounts, NPIs, dates. The whole Class-2 catalog then runs under Microsoft's BAA (availability on the record; in force on the tenant a named look) at $25/month. **But `AS-Q4` ruled that the chronology drop zone stores extracted TEXT per version** (built, fixture-only) — so (c) is not a design choice this memo can make; it is a re-ruling only Michael can make, now that the price of the alternative is known. The challenger's own caveat is the honest cost: *"One pasted SOAP note into a text column undoes it."*

**Claude's default, put and not applied [v2]: pointer-only mail ingest, and no PHI text entering Supabase by any *new* path until `Q-API-1` is ruled with the price in view.** On `AS-Q4` as ruled, the first real chronology drop is the act that triggers the Team-plan cost — which is why `Q-API-1` is put *now*, ahead of that drop, rather than discovered at it; the drop zone itself stays exactly as ruled and built. And a flag that stands regardless of the choice: **the chronology drop zone (`AS-Q4`, built, fixture-only) stores extracted chronology TEXT in Supabase** — BUILD-STATE: *"the FILE IS NEVER STORED, only its text (`AS-Q4`)"* and *"THE AMENDMENT'S FIVE CARRY PHI — a chronology's extracted text above all"* — **so the first real drop puts PHI in the database before any mail integration exists** (today: *"NO REAL CLIENT DATA HAS EVER ENTERED THE APP"*). The Supabase BAA question is therefore not an integration question at all; it is a pre-condition of the first real chronology drop, and it is not on the go-live floor because the floor is *"GO-LIVE = real case/party/client/SOL data hand-entered into the core app, NOTHING MORE."* **`Q-API-1`, §6.**

## §2 — HOW INTEGRATIONS FIT THIS APP: five rules, all proposed

**Rule 1 — three execution places, chosen by the data class, never by convenience.**

| Place | Runs when | Credential | Carries | Examples |
|---|---|---|---|---|
| **Browser SPA** (exists) | a tab is open; user-initiated | delegated, per-browser, no secret | anything Michael can already see | calendar push; on-demand mail read; on-demand QBO read (the memo notes QBO's read path *can* be user-initiated); Graph PDF conversion; OneDrive window |
| **Integration runner** (proposed, §1) | on schedule or on webhook | app-only certificate; Edge Function secrets; Vault | PHI only under the Supabase BAA (§1.2) | mail intake; LegiScan; statute refresh; e-signature and SMS webhooks; QBO token rotation; backup verification |
| **P1 local service** (designed, T3) | when the laptop is awake | none leave the machine | PHI-touching AI | transcription; bill/EOB ingestion (Phase 1b); a local model if `H12-v` goes that way |

**[v2]** Two further places exist if `Q-API-2` chooses them — an **Azure runner** (Functions/Container Apps, Managed Identity, Key Vault, Event Hubs) and **Power Automate flows** — both inside Microsoft's tenant; §1.3 has the table.

**Rule 2 — inbound events are STAGED, never auto-filed.** The transcript inbox already embodies this (auto-file OFF, D1). Every inbound integration lands in one staging surface — the existing `/inbox` generalized from "transcript staging" to "everything that arrived" — with a source, a confidence, a suggested matter, and a confirm control. The `email-workflow-requirements.md` constraints apply on their face: hard ignore layer first, dedupe on the pipeline's key, human routing for client mail. Nothing writes a calendar event, a deadline, or a party record without a click, with one recorded exception the heartbeat design already names: an e-filing acceptance from a known sender may auto-arm the next thread (`case-heartbeat-design.md` §6 #5) — and even that arms a nudge, not a record.

**Rule 3 — outbound writes are idempotent and reconciled.** The Outlook duplicate defect is the exhibit: a push with no durable external id strands a copy forever. Every outbound integration gets an `external_refs` row (`system`, `external_id`, `local_table`, `local_id`, `last_synced_at`, `sync_status`) *before* the remote call, keyed so a retry finds its own prior attempt; the calendar push migrates onto it (fixing the defect's class, whatever its cause). The record notes the substrate is absent today (§0 item 13) — this is the one schema act every integration shares, and it is a migration only when Michael authorizes one.

**Rule 4 — PHI class is decided per integration before auth is designed.**

| Class | Meaning | Members |
|---|---|---|
| **0 — never PHI** | the traffic is public law or the firm's own credentials; a client is never named | LegiScan, statute fetch, eCFR, CourtListener (authority cites only — the design says *"never client names, facts, or case details"*), PACER, NPPES, Postmark auth mail, Bookings availability |
| **1 — confidential, not PHI** | client identity and money or filing facts, privileged but not health data | QuickBooks, LawPay-class payments, e-filing envelope notices, process serving, e-signature of engagement/fee documents, court dockets |
| **2 — PHI** | health information or documents that carry it | mail intake on a PI file, OneDrive documents, chronology text, medical-records fax, client SMS, the model call, the backup copy, e-signature of HIPAA authorizations |

Class 2 needs a signed BAA with **every** vendor in the path — including the platform holding the data — and Postmark, which *"cannot sign any Business Associate Agreements"* (Postmark Support, "Is Postmark HIPAA compliant?" **[FETCHED 2026-09-08]**), is therefore never a channel for anything but sign-in links. **App notifications that could name a client or a provider go out through Graph `Mail.Send` from Michael's own mailbox, not through Postmark** — which is a design consequence worth writing down now, before a "send me a reminder" feature reaches for the SMTP that is already wired.

**Rule 5 — Microsoft is the tenant; everything else is a vendor.** Graph is the default for calendar, mail, files, contacts, chat, call metadata, scheduling and PDF conversion. A non-Microsoft vendor enters only where Microsoft has no surface (payments, SMS with attachments, fax, e-signature webhooks, legislative data, case law, backup independence) — and each such vendor is a credential to custody, a BAA to sign or a data-terms review, and a row in `external_refs`.

## §5 — WHERE CLAUDE DISAGREES WITH SOMETHING ON THE RECORD, SAID PLAINLY

1. **The WF spec treats the server-side identity as a single question with one answer.** It may be two: an *interactive* identity (delegated, browser) and a *background* identity (app-only, runner) can coexist on two registrations, and most of the value in §3 comes from the delegated half — PDF conversion, on-demand mail bodies, the OneDrive window, `Mail.Send`, QBO reads — which needs no runner at all.
