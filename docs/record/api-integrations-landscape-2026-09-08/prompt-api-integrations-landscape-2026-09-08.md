# PROMPT — API integration landscape for a solo Texas practice's case-management app

*Copy everything below the line into the other model. It is self-contained: the model needs no access to the repository, and nothing in it identifies a client or a matter. Prepared 2026-09-08 Central for Michael Brennan; the original one-paragraph prompt is superseded by this text.*

---

You are a senior software architect advising a solo-practitioner attorney who is designing and building his own case-management application. He wants a complete, current, and honest map of the API integrations the application could carry, and a concrete proposal for how each would work inside *this* application — not a generic list for a hypothetical product. Read the context below before answering; where a fact is missing, say "not established" rather than assuming it.

## 1. The practice

- Solo attorney, San Antonio (Bexar County), Texas. Practice areas: personal injury (motor-vehicle and trucking collisions among them), civil litigation, criminal defense (a large share of it court-appointed, across several counties), and probate. Occasional federal work in the Western District of Texas. A paralegal hire is expected later; the application is single-user today and multi-user later.
- Productivity stack is **Microsoft 365 only**: Exchange Online/Outlook, OneDrive, Teams, Entra ID. **No Google product of any kind will be integrated — not Gmail, not Drive, not Calendar, not Maps, not Google Cloud.** Where a productivity or platform integration is needed, Microsoft Graph and the Microsoft tenant are the default.
- Other systems in daily use: **CloudLex** (the current commercial case-management system and the origin of every document; CloudLex pushes a copy of each document to OneDrive), **QuickBooks Online** (the money system of record, used by the bookkeeper and tax preparer; IOLTA trust and operating money are both in play), **Lexis+** and **vLex Fastcase** for legal research, **eFileTexas** (through a certified e-filing service provider) for filing and e-service, one regular process-serving vendor reached by email, and a hardware voice recorder for dictation and call notes.
- Operational reality lives in email: roughly 40–45 messages on a weekday. A sanitized survey of that mailbox found seven recurring multi-email pipelines: e-filing envelope lifecycle; e-signature lifecycle; letter-of-protection medical pipeline (referral → treatment → records and bills); settlement pipeline (negotiation → release → check → lien payoffs → dismissal); criminal appointment pipeline (appointment notice → discovery portal → plea offer → docket); records retrieval (request → custodian delays → fulfillment); and service of process (assignment → attempts → return). Deadline extraction from attachments and prose is the highest-value function. New matters arrive by indigent-defense appointment orders and attorney referrals, not web leads.

## 2. The application as it stands

- **Stack:** React/TypeScript single-page app; **Supabase** (Postgres, Auth, Edge Functions) on the Pro plan; a data-adapter layer with a localStorage demo mode and a Supabase mode, so every feature must work in both; row-level security on every table. Sign-in is magic-link only, sent through custom SMTP on **Postmark** from the firm's domain.
- **The only third-party auth surface today** is one Microsoft Entra app registration used as a **public-client browser SPA (MSAL, PKCE)** holding a single delegated scope, `Calendars.ReadWrite`, with per-browser tokens and **no client secret**. The application has **no server-side identity** and no background process: nothing runs when a browser tab is closed. Three Supabase Edge Functions exist in the code — a statute-text proxy, a LegiScan poller, and a stubbed drafting-model function that names one vendor-neutral secret and calls no vendor — the first two are recorded as **not deployed**, and the stub is not in use (the app's drafting path runs a fixture writer with zero network calls).
- **Built and working:** case/party/client model with a firm-wide contact directory (roles, aliases, duplicate flags); calendar with a **one-way push to Outlook via Microsoft Graph** into a dedicated calendar (create, edit, cancel; per the setup notes each event carries a matter reference in an extended property; one known defect — the first edit of an event that was pushed at connect time duplicates it in Outlook); a legal-rule registry with attorney-only verification; a Texas statute viewer (cache-on-demand against the Legislature's official site); a LegiScan-based pending-bill tracker (API key held as a Supabase secret; poller written, not deployed); an order-of-appointment intake that parses one county's digital appointment-order form into a draft criminal matter (other counties' scanned packets are manual entry); a medical-bills module with Medicare fee-schedule benchmarks imported from CSV; a form engine that generates .docx instruments from tokenized templates; a disclosures generator whose model call is stubbed behind that server-side function — **no vendor is wired and no real record can reach a model until a BAA is signed**; a per-client medical-chronology drop zone that keeps only the extracted **text** of the dropped file (the file itself is never stored) — built and exercised on fictional fixtures only, so no PHI is in the database today, but the first real chronology will put PHI there; a transcript staging inbox designed for a **local** NVIDIA speech-to-text pipeline on the attorney's own GPU laptop (no cloud transcription, by design).
- **Designed or researched but not built, each behind a stated gate:** the seven email pipelines above (gated on a server-side identity and on a mail scope the registration does not hold); a QuickBooks Online link ("link, don't rebuild; read first; sandbox until go-live" — research found QuickBooks offers no read-only scope, requires a confidential client with a rotating refresh token, and does not enforce trust/operating separation); a CourtListener / Free Law Project citation-graph integration (designed in three layers but **barred from the app until the attorney settles with Free Law Project whether internal tooling supporting a firm's operation counts as commercial use under their API terms**); document storage and mobile document access (the trigger is the phone, where the app would be the only path to a matter's documents; the PHI boundary for phone-in-public access is an open question); a Microsoft-independent third backup copy under a BAA (object storage favored; $50/month ceiling; restore must not route through Microsoft); a communications log (research found that Teams chat reads need Microsoft's protected-API approval, that the firm's client-facing number is a cell phone with no API, and — on a forum-grade source not yet confirmed against vendor documentation — that Teams SMS threads are not exposed through Graph); a rules-based deadline engine; and firm-level recurring obligations (bar dues, malpractice renewal, CLE, backup checks).
- **Already ruled out:** Slack (Teams on the existing tenant would serve any team-messaging need); a vendor AI research assistant as a source of verification; filing *through* the app (in Texas that means becoming or contracting with an OCA-certified e-filing service provider — a commercial and regulatory undertaking, not an API key — so it is out of scope unless your answer shows it is worth it).

## 3. Hard constraints on any proposal

1. **No Google, anywhere.** Microsoft 365 is the tenant.
2. **HIPAA and privilege.** PI files carry protected health information; every file carries privileged material. PHI never goes to a third party without a signed Business Associate Agreement, and "the vendor says it is HIPAA-compliant" is not a BAA. Anything AI-related that touches PHI runs locally by design, except the drafting model call, which is a server-side function gated on a BAA-covered vendor. Emails from clients get human routing, never templated automation.
3. **Credential custody.** Static keys live in Supabase Edge Function secrets — never in the browser, never in the repository. Any integration that needs a client secret, a certificate, or a rotating refresh token needs a server-side home that can also *write* the new value. Treat **"does this application acquire a server-side identity, and of what shape?"** as the first-order question for every background integration, and answer it before proposing things that depend on it.
4. **Nothing is decided by a document.** Every recommendation is a proposal until the attorney rules on it. Present options as starting points, not a menu — his answer is often a composite. Mark each integration **EXISTS / DESIGNED-UNBUILT / NEW** against the description above, and say what must be true before it can be built and who must act (his consent on the Entra registration, a BAA, a vendor account, a plan upgrade).
5. **Legal authority is retrieved, never verified, by software.** Case-law, statute, and regulation integrations may fetch, cache, diff, and flag; only the attorney verifies a proposition.
6. **Solo now, multi-user later** behind a professional security review; design so a paralegal can be added without re-architecting identity.
7. **No real client data** touches any development artifact; sandboxes and fictional fixtures until the go-live gates are met.
8. **Vendor facts must be current and sourced.** For each vendor claim (BAA availability, scopes, rate limits, pricing model, API existence), name the page you rely on and its date, and say "not established" where you could not confirm it. Do not invent APIs; several systems in Texas practice have portals and no API at all.

## 4. What to produce

**A. Integration architecture for this app.** Where each class of integration executes — the browser (user-initiated, delegated permissions), a server-side function (background, app-only credentials), or the local GPU machine (PHI-touching AI) — and the auth model, credential custody, and failure handling for each. Include how inbound events are staged for human confirmation rather than auto-filed, how outbound writes are made idempotent and reconciled, and how PHI-class and non-PHI integrations are kept on different paths. Answer the server-side-identity question concretely (for example: a second, confidential-client Entra registration scoped with Exchange Online RBAC for Applications to the attorney's mailbox only, run from scheduled Supabase Edge Functions — or a better shape, with reasons).

**B. The catalog.** One row per integration, grouped: (1) Microsoft 365 / Graph — calendar, mail intake, sending mail as the attorney, contacts, OneDrive/SharePoint files and document conversion, Teams, Bookings, sign-in; (2) the app's own platform — Supabase (including whether its BAA/HIPAA add-on is needed once PHI is stored), Postmark; (3) legal authority and legislative — Texas statutes, LegiScan, eCFR, CourtListener/Free Law Project, PACER; (4) courts and filing — eFileTexas, Texas court-record portals, county dockets, appointment orders; (5) evidence and records — TxDOT crash reports, medical-records retrieval, fax, NPPES/CMS data, hospital price-transparency files; (6) money — QuickBooks Online, a legal-payments processor, trust-accounting boundaries; (7) documents and signatures — e-signature providers including the Microsoft-native option, PDF conversion; (8) communications — SMS, fax, voice/call records, transcription; (9) AI/model vendors under a BAA; (10) backup and storage. For each row: purpose in this practice; vendor/API; direction (read, write, webhook); auth model; PHI class (never carries PHI / may carry PHI → BAA required); status (EXISTS / DESIGNED-UNBUILT / NEW); the gate that must clear first; who must act; rough effort (S/M/L).

**C. Sequencing.** Three waves tied to the gates, each opening with the single decision the attorney must make for that wave. Put cheap, PHI-free, high-value items first; name what should *not* be built and why.

**D. Open questions for the attorney**, numbered, in full sentences, each answerable in one line.

Be thorough; tables are welcome; no filler. Where you disagree with a stated design choice, say so and give the reason — but do not silently redesign what is already ruled.
